# providers

**Purpose:** the provider model (ADR-0010, spec Modules 15–17, skill gps-provider-model): GPS tracking businesses register, are approved by the platform, brand the app, create their end customers and run them.
**Tables:** `provider_profiles` (registration, lifecycle, terms, branding), `customer_entitlements` (per-customer limits, stored; enforced from M10), `member_customer_scopes` (staff limited to some customers); `organizations.provider_id` and `provider_id` on every tenant table (filled and checked by the database).
**Endpoints:** public `POST /providers/register` (202, same answer for a known email), `GET /branding/resolve?slug=` (display data only; unknown = neutral brand) · platform `/admin/providers` list/get/approve/reject/suspend/reactivate (`platform.providers.*`, step-up) · provider console `/organizations/:providerId/provider/{profile,branding,customers,customers/:id,customers/:id/suspend|reactivate|limits,staff/:memberId/scope,fleet/snapshot}` · `GET /organizations/:id/branding` · customer owner `GET /organizations/:id/access-log`.
**Lifecycle:** `provider-lifecycle.ts` is the only table of allowed status changes (PENDING_VERIFICATION → PENDING_APPROVAL → TRIAL|ACTIVE|REJECTED; TRIAL|ACTIVE|GRACE → SUSPENDED → ACTIVE). Changes are compare-and-set and audited.
**Rules:** customers of an unapproved provider are sandbox organizations (no real device can be registered in one); a suspended provider is blocked and its customers get a neutral "contact your provider" answer while ingestion continues; provider staff are not members of customer organizations — their access is derived from their role, limited to their customer scope, and written to the customer's access log.
**Not yet:** logo upload (needs file storage), custom domains, staff-scope UI, customer transfer between providers and plans/billing (M10), regulator organization (M9).
